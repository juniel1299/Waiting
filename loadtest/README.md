# loadtest: 마지막 자리·취소/승격 동시성 검증

로컬 **실제 PostgreSQL**(docker compose) 로 동시 요청을 단계적으로 늘려 예약·대기·취소/승격의 정합성을 확인한다.

## 도구 선택

Node 내장 `fetch`(undici) 스크립트 하나(`loadtest.mjs`). 이 저장소는 이미 Node(프런트)와 Docker(DB)를 쓰므로 설치할 것이 없고,
부하 도구(k6 등)로는 번거로운 "실행 후 DB 를 SQL 로 대조"를 같은 스크립트에서 바로 할 수 있다. 대신 수천 RPS 급 측정용 도구는 아니다.

## 실행

```bash
docker compose up -d          # 저장소 루트
loadtest/run.sh               # 기본 단계 10, 50, 100, 200, 400
LEVELS=10,50 loadtest/run.sh  # 단계 지정
SCENARIOS=C loadtest/run.sh   # 시나리오 지정 (A, B, C 중, 기본 전부)
loadtest/run.sh --selftest    # checks.sql 이 위반을 잡는지 확인 (한 번 실행한 뒤)
```

`run.sh` 순서:

1. 같은 postgres 컨테이너에 전용 DB `daumjari_load` 를 지우고 새로 만든다 (개발 DB `daumjari` 는 건드리지 않음).
2. 그 DB 로 백엔드를 `18090` 포트에 띄운다. 가입·로그인 한도만 실행 인자로 높인다 (`application.yml` 기본값은 그대로).
3. `loadtest.mjs`: 계정 605개를 가입·로그인해 두고, 단계마다 새 회차(SQL 로 생성)에 요청 N개를 한꺼번에 보낸다.
4. `checks.sql` 로 DB 를 검사한다 (모두 0행이어야 정상). 끝나면 백엔드를 끈다.

결과: `results/<실행시각>.json` (단계별 수치·응답 코드·승격 id·대기 순서), `results/checks-*.txt` (SQL 결과), 정리본 [`results/2026-11-21-local.md`](results/2026-11-21-local.md) (A·B), [`results/2026-11-21-local-capacity.md`](results/2026-11-21-local-capacity.md) (C).

## 시나리오

| 이름 | 내용 | 통과 조건 |
|---|---|---|
| A 마지막 자리 | 정원 1 회차에 N명 동시 예약 | 확정 정확히 1건(DB 대조), 나머지 `409 SESSION_FULL` |
| B1 동시 대기 | 정원 5 마감 회차에 N명 동시 대기 | 모두 `201 WAITING` |
| B2 취소·승격 혼합 | 확정자 5명 취소 + 신규 예약 N/4 + 신규 대기 N/4 동시 | 승격된 5건 = B1 에서 먼저 대기한 5건(id 순), 신규 예약 모두 `409 SESSION_FULL`, 남은 대기 수 일치 |
| C1 동시 대기 | 정원 1 회차에 N명 동시 대기 | 모두 `201 WAITING`, 대기 순번 = id 순 1..N |
| C2 증설·축소·취소 혼합 | 운영자 정원 1→6 증설 + 정원 →1 축소 + 확정자 취소 + 신규 예약 N/4 + 신규 대기 N/4 동시 | 최종 정원 6, 확정 = 대기 순번 1~6, 축소는 `200` 또는 `409 CAPACITY_BELOW_CONFIRMED`, 신규 예약 모두 409 |

시나리오 C 의 운영자는 부하 전용 DB 에 참가자로 가입한 계정을 SQL 로 `OPERATOR` 로 바꿔 쓴다 (시드 비밀번호를 쓰지 않음).

예상된 응답(위 코드)과 예상 못한 오류(5xx, 타임아웃 30초, 연결 오류, 그 밖의 코드)를 따로 센다.

## SQL 정합성 검증 (`checks.sql`)

| # | 검사 | 정의 |
|---|---|---|
| ① | 정원 초과 | 회차별 `CONFIRMED` 수 > `capacity` |
| ② | 활성 신청 중복 | 같은 (회차, 계정)에 `CANCELLED` 가 아닌 신청 2건 이상. DB unique 인덱스 `ux_reservation_active` 가 이미 막으므로 최후 확인용 |
| ③ | 대기 추월 | 시작 전 회차에서, 아직 `WAITING` 인 신청보다 **id 가 큰** 신청이 `CONFIRMED` |
| ④ | 승격 누락 | 시작 전 회차에서 확정 수 < 정원인데 `WAITING` 이 남음 |

③의 근거와 한계: id 순서가 곧 신청 순서다(신청은 회차 행 잠금 아래 하나씩 들어감). 대기자가 있으면 신규 예약은 막히고 승격은 id 순이므로,
순서대로 승격된 대기자는 남은 대기자보다 id 가 작아 걸리지 않는다. 반대로 대기를 건너뛴 직접 확정이나 순서를 어긴 승격은 남은 대기자보다
id 가 커서 걸린다. 상태 변경 이력을 남기지 않으므로 "직접 확정"과 "늦게 승격" 을 구분하지는 못하고(둘 다 위반으로 잡힘), 대기자가 모두
승격·취소되어 `WAITING` 이 하나도 남지 않은 회차의 과거 순서는 검사할 수 없다. 그래서 B2 는 승격된 id 를 B1 의 대기 순서와 직접 비교한다.

`checks-selftest.sql` 은 한 트랜잭션에서 ①·③·④ 위반을 일부러 만든 뒤 검사하고 되돌린다 (2026-11-21 실행: 각 1행씩 검출, ②는 unique 인덱스로 만들 수 없음).
