이력서·자기소개서 대화에 넘기기 위한 **근거 자료**다. 이력서에는 지원 직무에 맞는 핵심 성과 3~4개만 골라 쓴다. 면접에서 직접 설명할 수 있는 수준으로만 적었고, 세밀한 측정값은 README·포트폴리오 문서에 있다. **[직접 작성]** 은 본인이 채울 칸이다.

## 1. 한 줄 소개

정원이 찬 스터디 회차에 대기를 걸어 두면 빈자리가 생길 때 **대기 순서대로 자동 확정**되는 예약 서비스로 시작해, 게시판·알림·모임(채팅·사진첩)까지 갖춘 스터디 플랫폼으로 넓힌 개인 프로젝트. 무료 서비스만으로 공개 배포했고(월 0원), 가입 없이 핵심 흐름을 체험하는 데모를 만들었다.

- 공개 서비스: https://waiting-mauve.vercel.app (가입 없이 `데모 체험하기`)
- 시연: https://waiting-mauve.vercel.app/tour
- 저장소: `juniel1299/waiting`

## 3. 기술 스택

- 프런트: Next.js(TypeScript)
- 백엔드: Java, Spring Boot, Spring Security(세션 로그인)
- DB: PostgreSQL
- 테스트: JUnit + Testcontainers(실제 DB로 테스트), Playwright(브라우저 테스트)
- 배포: Vercel(프런트) → Render(백엔드) → Neon(DB), 모두 무료 요금제

## 4. 주요 기능

- **예약:** 예약·대기·취소, 빈자리가 나면 대기 순서대로 자동 확정, 화면 자동 갱신
- **데모:** 가입 없이 버튼 하나로 나만의 체험 회차를 만들어 "대기 → 빈자리 → 확정"을 직접 해 볼 수 있음
- **커뮤니티:** 게시판·공지, 댓글·답글·추천·멘션, 알림함
- **모임:** 모임 만들기 신청·승인·가입, 역할(만든 사람·운영자·회원), 모임 게시판, 채팅, 사진첩
- **회원:** 프로필·공개 프로필, 즐겨찾기, 카카오·네이버 계정 연결
- **운영:** 운영자 대시보드, 회원 정지·탈퇴 처리, 모임 승인
- **화면:** 모바일 대응, 라이트·다크 모드

## 5. 문제 해결 사례

1. **동시에 몰려도 정원을 넘지 않는 예약**
   마지막 한 자리에 여러 명이 동시에 예약하면 정원을 넘을 수 있었다. 회차 단위로 DB 잠금을 걸어 예약 잠금의 경합 범위를 해당 회차로 제한했다. 또 취소만 반영되고 승격이 실패하면 대기자가 확정되지 않은 상태가 남을 수 있어, 취소와 다음 대기자 확정을 같은 트랜잭션으로 처리하고 실패하면 함께 롤백했다.
   검증(내 PC, 실제 PostgreSQL): 정원 1인 회차에 최대 400건을 동시에 보내도 확정은 1건이었고, 대기자 400명 상태에서 취소·정원 변경·신규 요청을 섞어도 정원 초과·중복·대기 추월·승격 누락이 0건이었다.
2. **가입 없이 체험하는 데모**
   방문자는 가입하지 않지만, 핵심 흐름을 보려면 "마감된 회차"와 "취소해 줄 사람"이 필요했다. 방문자마다 체험용 회차와 샘플 참가자를 자동으로 만들고, 실제 예약 로직을 그대로 쓰게 했다. 방문자끼리 서로의 데이터는 보이지 않고, 30분 후 만료되며 정리 작업이 관련 데이터를 삭제한다.
3. **무료 서버가 잠들어 있을 때의 사용자 경험**
   무료 서버는 한동안 요청이 없으면 잠들어 첫 응답에 몇 분이 걸린다. 화면에서 "서버를 깨우는 중" 안내와 자동 재시도를 하고, 기다리는 동안 서버 없이도 열리는 시연 페이지를 볼 수 있게 했다.
4. **권한이 바뀌면 바로 반영**
   운영자 권한을 회수하거나 모임에서 탈퇴하면, 이미 로그인한 화면에서도 다음 요청부터 막혀야 했다. 권한을 로그인 정보에 저장하지 않고 요청마다 DB에서 확인하게 했다. 삭제와 글쓰기가 동시에 일어나도 지워진 모임의 글이 남지 않게 처리 순서를 맞췄다.
5. **모임 채팅 (폴링 방식)**
   현재 인증·프록시 구조와 무료 배포의 운영 복잡도를 고려해 실시간 연결 대신 증분 폴링을 택했다(채팅 3초, 회차 상세 5초). 새 메시지만 이어 받고 위로 올리면 이전 기록을 불러온다. 내 PC에서 120건을 거슬러 읽는 동안 30건을 동시에 보내도 중복·누락이 0건이었다.
6. **사진 업로드의 개인정보·용량**
   사진에 담긴 촬영 위치 정보를 지우고 크기를 줄여 저장했다. 휴대폰 사진(HEIC 등) 형식과 용량 제한을 화면에서 미리 안내했다. 실제 아이폰으로 위치 정보가 지워지는지 확인했다.
7. **배포·운영 중 문제 대응**
   Render 빌드 중 Maven Central 이 HTTP 429 를 반환해 의존성 다운로드에 실패했다. 미러 저장소를 먼저 쓰고 의존성을 빌드 캐시에 두어 해결했다. 공개 사이트 점검 중 발견한 로그인 오류도 원인을 찾아 고쳤다.
8. **iPhone Safari 의 날짜 입력 영역 넘침**
   iPhone Safari 에서 날짜 입력 영역이 넘치고 같은 줄 버튼 높이가 달라 보였다. Safari 엔진(WebKit)으로 확인해 선택창 높이가 맞지 않는 원인을 찾아 공통 스타일에서 고쳤다. 날짜 넘침 자체는 에뮬레이션에서 재현되지 않아, Safari 의 날짜 입력에 대한 방어 규칙을 넣고 배포 후 실제 iPhone 에서 확인했다.

## 6. 개발 방식·검증

- 기능마다 **테스트를 먼저 쓰고 → 구현 → 배포 → 공개 사이트에서 다시 확인**하는 순서로 진행했다(일부 화면 테스트는 구현 뒤에 작성).
- 백엔드는 실제 PostgreSQL로 테스트하고, 브라우저 테스트로 데스크톱·모바일 화면을 확인했다. 한 번에 돌린 전체 실행(2026-11-28): 백엔드 854·브라우저 테스트 162·프런트 단위 57 모두 통과 — 근거 `loadtest/results/2026-11-28-test-run.txt`(실행 커밋·환경 기록).
- 실제 아이폰과 실제 카카오·네이버 계정으로도 확인했다.

## 7. 이력서 문장 후보

- 동시 예약이 몰려도 정원을 넘지 않도록 DB 잠금과 트랜잭션으로 예약·대기·자동 확정 기능 구현
- 가입 없이 핵심 흐름을 체험할 수 있는 방문자별 데모를 실제 서비스 로직 위에 구현
- 예약 서비스를 게시판·알림·모임 채팅·사진첩을 갖춘 플랫폼으로 단계적으로 확장
- 무료 클라우드(Vercel·Render·Neon)로 배포하고, 서버 절전 시 안내·자동 재시도로 사용자 경험 보완
- 테스트 우선 개발과 배포 후 점검으로 품질 관리, 실제 기기에서 발견한 화면 문제를 Safari 엔진으로 확인해 수정

## 8. 한계 (면접 대비)

- 실제 사용자 수 같은 운영 지표는 없다.
- 성능 테스트는 내 컴퓨터(로컬)에서만 했다.
- 채팅은 실시간 연결 대신 증분 폴링(3초)이다. 동시 접속 증가에 따른 조회 부하와 갱신 지연을 측정해 SSE·WebSocket 전환을 검토할 계획이다.
