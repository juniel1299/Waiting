## 1. 한 줄 소개

정원이 찬 스터디 회차에 대기를 걸어 두면 빈자리가 생기는 순간 **대기 순서대로 자동 확정**되는 예약 서비스로 시작해, 게시판·알림·모임(채팅·사진첩)까지 갖춘 스터디 플랫폼으로 넓힌 개인 프로젝트. **월 0원** 무료 구성으로 공개 배포했고, 가입 없이 핵심 흐름을 눌러 보는 방문자별 데모를 실제 예약 로직 위에 만들었다.

- 공개 서비스: https://waiting-mauve.vercel.app (가입 없이 `데모 체험하기`)
- 시연: https://waiting-mauve.vercel.app/tour (예약 흐름 20초·모임 16초 영상 + 화면 자료, 서버가 잠들어 있어도 열림)
- 저장소: `juniel1299/waiting` (README 맨 위에 기능표·최근 변경·검증 기록)

## 3. 기술 스택과 구조

- **프런트:** Next.js 16(App Router, TypeScript), Zustand(화면 상태), 의존성 없는 SVG 차트, Playwright e2e
- **백엔드:** Java 17, Spring Boot 4.1(JDBC·JPA), Spring Security(서버 세션 + 쿠키 CSRF), Spring Session JDBC, Flyway, JUnit + Testcontainers(실제 PostgreSQL)
- **DB:** PostgreSQL 16 (Neon)
- **배포(월 0원):** Vercel Hobby(프런트·`/api` 프록시, sin1) → Render Free(Spring Boot, Docker, Singapore) → Neon Free

```
브라우저 → Vercel (Next.js, /api Route Handler 프록시: 실제 IP 재기록 + 공유 비밀 토큰)
        → Render Free (Spring Boot, 토큰 없는 직접 호출 403)
        → Neon Free (PostgreSQL: 예약·세션·게시판·채팅·사진)
```

## 5. 문제 해결 사례 (근거 수치 포함)

1. **마지막 자리 동시 예약·취소 승격 정합성**
   - 문제: 동시에 예약하면 정원을 넘기고, 취소와 승격 사이에 신규 예약이 끼면 대기자가 밀린다.
   - 방식: 회차 행 `SELECT … FOR UPDATE` 아래에서 예약·대기·취소를 판단하고, 취소와 첫 대기자 승격을 같은 트랜잭션에서 처리(실패하면 취소까지 롤백). 활성 신청은 부분 unique 인덱스로 한 건.
   - 결과(로컬 실제 PostgreSQL): 정원 1에 동시 10~400건 → 모든 단계 확정 정확히 1건, 나머지 409, 예상 못한 오류 0. N=400 870 req/s·p95 429ms. 대기자 400명 + 혼합 요청 203건 p95 288ms. SQL 정합성 검사 4종(정원 초과·중복·대기 추월·승격 누락) 0행.
2. **가입 없는 방문자별 데모**
   - 버튼 한 번에 방문자·샘플 참가자·마감 회차가 생기고, 실제 취소·승격 코드로 "대기 → 빈자리 → 확정"을 보여 준다. 체험끼리는 `demo_trial_id` 로 격리(다른 체험 회차는 404), 30분 뒤 통째로 정리, IP 당 15분 10회 제한.
3. **무료 서버 절전 대응**
   - 프록시가 85초에 끊고 `503 + Retry-After`, 화면은 안내와 함께 최대 5분 자동 재시도, 기다리는 동안 백엔드 없이 열리는 `/tour` 를 새 탭으로. 약 55분 무요청 뒤 클릭부터 체험 화면까지 170.9초(1회 측정, 조건 기록), 깨어 있을 때 2.1초.
4. **"지금" 권한과 삭제 정합성 (커뮤니티·모임)**
   - 권한 주체가 운영자·모임 생성자·모임 운영자·회원·데모·비회원으로 늘어 화면 숨김만으로는 못 막는다 → 모든 판단은 서버, 역할은 세션에 두지 않고 요청마다 DB 에서 다시 읽음. 회수·탈퇴가 이미 로그인한 세션의 다음 요청부터 반영.
   - 잠금 순서 통일(모임 → 글 → 댓글) + FK CASCADE 물리 삭제. 경합 테스트(각 20회, 실제 PostgreSQL)에서 생성자 이전 두 건 → 생성자 1, 삭제 vs 글·댓글·추천·가입 → 고아 0. 경합 테스트로 조인 + `FOR UPDATE` 재확인 버그를 찾아 고침.
5. **알림의 일관성**
   - 알림은 원인 변경과 같은 트랜잭션에서만 쓰고(`Propagation.MANDATORY`), 사건 열쇠 unique 로 재시도에도 한 번. 열 때 그 순간 권한을 다시 확인. 승격이 롤백되면 알림 0.
6. **모임 채팅 (폴링 + 커서)**
   - Vercel WebSocket 은 베타·Hobby 300초 제한이라 폴링을 택하고 근거를 문서화. 모임 단위 advisory lock 으로 순서·누락 없는 커서, 이전 기록은 `before` 역방향 페이지. 폴링과 이전 기록이 겹쳐도 중복·누락 없음을 100개 넘는 메시지로 검증.
7. **사진 업로드 (보안·용량)**
   - 확장자 대신 바이트 시그니처로 판별, EXIF(위치) 제거·방향 반영 후 1600px 재인코딩, CMYK·HEIC 는 이유를 안내. 층별 크기 한도(화면 4MB·Vercel 4.5MB·백엔드 5MB)를 맞춰 413 을 안내·재시도로 처리. 전역 용량 상한은 advisory lock 으로 동시 업로드에도 정확히. 실제 iPhone 에서 위치 정보 제거 확인.
8. **운영 장애 대응**
   - 운영 로그인 500(12자 아이디·JDBC 세션)을 공개 점검 중 발견해 수정(2026-11-21).
   - Render 빌드가 Maven Central 429 로 연속 실패 → Google 미러 + Docker 의존성 레이어 캐시 + `--offline` 빌드로 해결, 소스만 바꾼 재빌드에서 의존성 레이어 캐시 확인(2026-11-27).
   - Vercel 이 병합 커밋으로 Production 배포를 만들지 않은 것을 GitHub 상태로 찾아 수동 배포 절차로 해결.
9. **화면 품질 (실기기 제보 → 재현 → 공통 수정)**
   - iPhone 18 Pro 에서 날짜 입력 넘침·높이 불일치 제보 → WebKit(iPhone 에뮬레이션)으로 재현해 Safari 의 `select` 최소 높이 무시를 원인으로 찾고 공통 스타일에서 수정, 버튼·입력 44px·line-height 통일. 라이트·다크 모드(깜빡임 없는 적용, 다크 버튼 글자 대비 2.5:1 → 7.79:1).

## 7. 이력서 문장 후보 (직무별, 수치는 위 근거)

**백엔드**
- 마지막 자리 동시 예약 400건에서도 정원 초과 0을 보장하는 회차 행 잠금·같은 트랜잭션 취소/승격 설계 (로컬 PostgreSQL, 870 req/s·p95 429ms, SQL 정합성 검사 4종 0행)
- 권한 주체 6종(운영자·모임 생성자·모임 운영자·회원·데모·비회원)의 "현재 권한"을 요청마다 DB 에서 확인하고, 잠금 순서 통일·FK CASCADE 로 경합 시 고아 데이터 0 (경합 테스트 각 20회)
- 원인 변경과 같은 트랜잭션·사건 열쇠 unique 로 알림 중복·유실 방지, 채팅은 모임 단위 advisory lock 커서로 순서·누락 없는 폴링
- Render 빌드 429 장애를 Maven 미러·Docker 레이어 캐시·offline 빌드로 해결

**프런트엔드**
- 무료 서버 절전(최대 약 3분)을 503 안내·자동 재시도·백엔드 없이 열리는 시연 페이지로 흡수
- 보이는 탭만 5초 폴링·탭 복귀 즉시 갱신으로 다른 사용자의 취소에 따른 내 확정을 새로고침 없이 반영, 채팅 이전 기록 불러오기에서 스크롤 위치 고정
- iPhone 에서 제보된 화면 깨짐을 WebKit 으로 재현해 공통 컴포넌트에서 수정(입력·버튼 44px 통일), 깜빡임 없는 라이트·다크 모드와 WCAG 대비 4.5:1 이상을 e2e 로 검증

**풀스택**
- 예약 서비스를 게시판·알림·모임 채팅·사진첩 플랫폼으로 7단계 확장하며 단계마다 테스트 먼저 → PR → 배포 → 공개 검증, 월 0원 배포 유지
- 가입 없는 방문자별 데모를 실제 도메인 로직 위에 만들어 시연이 곧 검증이 되게 설계 (체험 격리·30분 정리·IP 제한)

## 8. 한계·하지 않은 것 (면접 대비)

- 공개 서버 부하는 측정하지 않았다(무료 서버). 성능 수치는 모두 로컬.
- 실제 사용자 수·사업 지표는 없다.
- 운영자 로그인 화면의 화면 배치, 로그인이 필요한 채팅·사진 공개 회귀는 사용자 확인 대기 또는 로컬 테스트만.
- 실시간은 폴링(최대 몇 초 지연). Sentry 는 코드만 있고 꺼져 있다. 최초 소셜 가입·모임 강퇴는 없다.
